# 业务身份 QoS 验收

入口：[hg-qos-scenarios.py](hg-qos-scenarios.py)。连接配置与通用运行方式见
[README](README.md)。这套脚本使用部署中的业务策略，不安装临时分类、NAT、
整形或加速规则；HG 上仅使用互斥锁和状态查询。

## 端点与业务预期

[示例配置](configs/scenarios.example.json) 固定三档既定预期：

| 身份 | 运行位置 | DSCP |
| --- | --- | ---: |
| normal | fnOS 上已有的普通业务网络命名空间 | 7 |
| proxy | Mihomo 所在的独立网络命名空间 | 3 |
| background | fnOS 主机 | 8 |
| fakeip | 代理命名空间已存在、HG 可路由到的 Fake-IP 地址 | 3 |

运行时通过 Docker 获取 PID，并确认配置地址已存在；不会创建地址或改写路由。
容器名、接口名与地址须按实况修改。`interface` 是该命名空间接收测试报文的接口。
SSH 管理流量可以走跳板，测试报文仍须经过指定的 HG 端口。

Fake-IP 用例终止于命名空间内的专用监听端口，不调用 Mihomo 代理服务，不验证
域名规则、代理上游、互联网连接或代理带宽。TCP 使用串行请求/回显观察标记，
不是 SMB/NFS 性能基准。

## 用例矩阵

| 用例 | 验收内容 |
| --- | --- |
| 四种身份 × UDP 128 字节 | 小包，新连接与稳定阶段的双向标记 |
| 四种身份 × UDP 1400 字节 | 较大 UDP 报文，捕获 GRO/软件路径/加速切换时的遗漏 |
| 四种身份 × TCP 1400 字节记录 | TCP 数据双向标记与正常往返 |
| 代理、后台 × UDP/TCP DNS 端口例外 | 基础服务保持普通 DSCP 7 |
| 后台 × DHCP 单播端口例外 | 基础服务保持普通 DSCP 7 |
| `--congestion`：普通与代理争用 | 普通得到更高保护 |
| `--congestion`：代理与后台争用 | 代理得到更高保护 |

默认共 17 个低流量用例；拥塞模式另加四条流，分两组运行。每轮使用随机高
目的端口、随机高源端口和报文标识。DNS/DHCP 用例仅将 Win **源端口**设为
53/67，目的端口仍是探针高端口，不调用生产 DNS/DHCP 服务。端口被占用时报错，
不停止原服务；DHCP 广播、租约过程不在覆盖范围。

低流量响应默认没有 DSCP，由 HG 现行策略分类。UDP 新连接阶段和 TCP 前
32 条记录与主测阶段分别断言；任何实际观察到的错误标记都保留为 FAIL，不能
用后续稳定阶段正确覆盖冷启动错误。

## 观察与判定

- Linux UDP 使用 `IP_RECVTOS`；TCP 使用带 TCP 过滤器的 AF_PACKET 观察探针记录。
- Win UDP 回包用原始 IPv4 套接字；TCP 用 pktmon 在接收网卡边界捕获，按
  地址、端口、随机标识、记录号解析 pcapng 并去重。
- pktmon 仅捕获测试端口的 TCP，每包前 128 字节；沿用 512 MiB 文件上限。
  历史测试中 16 MiB 上限曾导致只有元数据的空捕获，因此未沿用。
- 主测每方向至少 100 个有效观测；冷启动至少一个。缺少 TOS、抓包覆盖不足
  99% 或已知接收缓冲丢包为 INCONCLUSIVE；任何观测到的错误 DSCP 为 FAIL。
- 正常低流量回显不足发送数的 99% 为 FAIL；若有已知探针接收缓冲丢包，则
  保守地记为 INCONCLUSIVE。TCP 回显成功不能替代 TCP DSCP 观察。

## 可选出口竞争

两档各请求出口速率的 65%，每组持续 2.5 秒；1G 配置下为各 650 Mbps。
先比较普通/代理，再比较代理/后台。它们会与同一物理出口的现有业务短暂争用。
大流量主测不回显，Win 暂停 UDP 原始抓包以减少发包负担；反向分类由低流量
用例验收，不能把大流量结果描述为反向出口竞争通过。

有效测量要求：

- 确认输入端口快于输出端口，输出速率与配置一致。
- 每档实际发速为出口速率的 59%～70%，总发送超过理论净荷容量的 115%。
- 总接收处于容量的 90%～107%；主测 DSCP 正确；端点和探针无已知接收丢包。

满足条件后，高档交付率至少 95%，且比低档高至少 20 个百分点才通过。
未形成有效竞争时为 INCONCLUSIVE，不把发包机瓶颈判成队列错误。冷启动错误
仍保留为业务失败，主测窗口的竞争结果另行报告。

## 清理与证据

HG 锁有 210 秒回收；Linux 探针最多 180 秒；Windows 客户端有 130 秒上限。
捕获前创建一次性 SYSTEM 清理任务，180 秒后只对本轮唯一 ETL 名称的会话
清理。程序拒绝接管已有 pktmon 会话或过滤器；若中途出现其他过滤器，保留并
报告清理错误。正常结束立即停止捕获，取回 ETL/pcapng，撤销任务。

可处理的中断会清理自己的程序、文件和锁；强杀/失联后由有限寿命停止流量和
捕获，临时文件可能仍需按报告中的唯一目录清理。测试连接自然超时，下一轮
使用新元组。报告不会因存在清理错误而给出 PASS。

## 当前边界

仅覆盖一个配置好的 IPv4 LAN 路径、Win 主动建连及其回包。即使该路径落在
默认 native VLAN，也不等于已验证 tagged VLAN、PCP 或安全隔离。其他端口、
PON/WAN、IPv6、IPTV、AP/WMM、fnOS 主动建连与真实应用语义仍需独立用例。
本次迁入未生成新的实机测试结果。

## 固件运行策略前置检查

两套脚本均记录 `airoha-qosctl get` 的模式、完整 DSCP 表和默认 priority 表。
新版示例包含 `qos_device: "lan1"` 与 `expected_qos`，要求运行在 DSCP 模式、
映射 7→4、3→2、8→0 且未报告 broken。配置不符或状态不可读时，在发包前
报 ERROR；不会根据实际结果改写测试期望。
旧配置可省略 `expected_qos`，此时记录状态而不强制新接口，缺失状态明确为
unknown。抓包通过仍不能证明内部 skb priority 或精确硬件队列；回归规则中的
`meta priority` 是注入的测试输入，并非对驱动改写该字段的要求。
